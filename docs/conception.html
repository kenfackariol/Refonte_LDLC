Refonte LDLC : Architecture de données NoSQL

Projet NSL NoSQL · Document de conception
Binôme : Ariol Kenfack et Raphael Deutou · Novembre 2026
Dépôt : github.com/kenfackariol/Refonte_LDLC

1. Contexte et démarche

LDLC (e-commerce high-tech : plus de 27 000 références, plus de 600 marques, des millions de visites mensuelles, jusqu'à 25 000 colis par jour) voit sa base relationnelle monolithique atteindre ses limites. Notre mission : concevoir l'architecture de données NoSQL de la nouvelle plateforme sur quatre périmètres fonctionnels.

Notre démarche repose sur trois principes vus en cours :

  • Persistance polyglotte : aucune base ne répond seule à des besoins aussi différents. Chaque lot reçoit le modèle de données adapté à ses contraintes.
  • Query-Driven Design : on part des requêtes métier pour construire le schéma, et non l'inverse.
  • Compromis CAP explicites : pour chaque donnée, on décide ce qui prime entre cohérence et disponibilité selon le coût métier d'une erreur.

Lecture CAP de l'ensemble. Nous choisissons CP là où une erreur coûte de l'argent (prix et stock du catalogue, intégrité du graphe), et AP là où l'indisponibilité coûte plus cher qu'une incohérence passagère (un panier qui ne répond pas fait perdre une vente ; un clic non compté n'a aucun impact). Les systèmes CP sont ensuite assouplis en lecture (lecture sur secondaires), et les systèmes AP sont durcis là où c'est nécessaire (LOCAL_QUORUM pour les commandes dans Cassandra). Le seul invariant financier strict, ne pas vendre un produit absent, est garanti par MongoDB (décrément conditionnel du stock).

Flèches pleines : appels synchrones pendant la requête de l'utilisateur. Flèches pointillées : flux asynchrones (événements, synchronisations, jobs).

Composants transverses

  • Serveurs API sans état : la session vit dans Redis, donc le load balancer n'a pas besoin de sticky sessions et on ajoute des serveurs lors des pics.
  • Kafka : bus d'événements. Un clic est déposé dans la file en moins d'1 ms puis consommé à son rythme. Il absorbe les pics et alimente plusieurs consommateurs (Cassandra, Neo4j).
  • Change streams MongoDB : propagent les modifications du catalogue vers Neo4j et invalident le cache Redis.
  • Jobs batch : top produits et top recherches (toutes les heures) ; réconciliation hebdomadaire de BOUGHT_WITH, mis à jour sinon à chaque commande.

Parcours d'une commande à travers les 4 bases

ÉtapeBase
Ajout au panier (HINCRBY)Redis
Prix relu et stock réservé (décrément conditionnel, primaire)MongoDB
Commande écrite de façon synchrone (LOCAL_QUORUM), puis confirméeCassandra
Publication « commande validée », suppression du panierKafka, Redis
Ajout au graphe, BOUGHT_WITH + 1 par paireNeo4j

Source de vérité : MongoDB pour le catalogue et le stock, Cassandra pour les commandes. La commande est écrite avant d'être confirmée, donc le client la voit aussitôt sur « Mes commandes ». Si le paiement échoue, le stock est remis (compensation) ; les écritures sont idempotentes et peuvent être rejouées. Les copies (sku, nom et prix dans Neo4j, cache Redis) sont alimentées par événements et peuvent avoir quelques secondes de retard, sans impact métier.

5. Lot 1 : Catalogue produits · MongoDB

Choix technologique

Les fiches ont des structures très différentes selon la catégorie (un CPU a un socket et des cœurs, une souris des DPI, un logiciel une licence) et doivent évoluer sans migration. Le modèle document stocke chaque fiche avec ses propres champs, sans schéma imposé. La fiche, lue très souvent, est récupérée en une seule lecture, sans jointure. Le relationnel imposerait une table par catégorie ou un modèle EAV ; Redis ne permet pas de filtrer sur le contenu ; Cassandra demande de connaître toutes les requêtes à l'avance, ce qui convient mal à une navigation par filtres multiples.

CAP : un replica set (3 nœuds, primaire unique) est CP. Nous réglons la cohérence par requête : secondaryPreferred pour l'affichage des fiches (quelques ms de retard acceptables, primaire soulagé lors des pics), primaire + readConcern: majority pour le prix au paiement, décrément conditionnel du stock sur le primaire (Q7), w: majority pour les écritures. Avec 27 000 produits, le sharding n'est pas nécessaire.

Schéma : collection products (extrait)

// Q4. Publier un avis : Subset + Computed en une écriture atomique sur le produit
db.reviews.insertOne(review)

  { $set: { "reviews.count": { $add: ["$reviews.count", 1] },
            "reviews.sum":   { $add: ["$reviews.sum", review.rating] },
            "reviews.recent": { $slice: [ { $concatArrays: [[resume], "$reviews.recent"] }, 5 ] } } },
  { $set: { "reviews.avg": { $round: [ { $divide: ["$reviews.sum", "$reviews.count"] }, 1 ] } } } ])

db.reviews.find({ productId: id }).sort({ createdAt: -1 }).skip(5).limit(10)

// Q6. Analyse : note moyenne par marque dans une catégorie
db.products.aggregate([ { $match: { "category.path": "composants/processeurs" } },
  { $group: { _id: "$brand.name", produits: { $sum: 1 }, note: { $avg: "$reviews.avg" } } },
  { $sort: { note: -1 } } ])

// Q7. Réserver le stock au paiement : filtre et décrément appliqués ensemble (atomique)
db.products.updateOne({ sku: "AMD-R7-7800X3D", "stock.quantity": { $gte: 2 } },
                      { $inc: { "stock.quantity": -2 } }, { writeConcern: { w: "majority" } })
// modifiedCount = 0 -> rupture : la commande est refusée. Plusieurs produits : session.withTransaction()

sku et slug (uniques) · {category.path, price.amount} (listes filtrées par catégorie et triées par prix : Q2, Q6) · brand._id · {attributes.k, attributes.v} · index texte name + description (français) · reviews : {productId, createdAt: -1}.

6. Lot 2 : Panier et sessions · Redis

Choix technologique

Redis conserve les données en RAM avec des opérations en O(1) : un aller-retour prend environ 0,1 à 0,5 ms. Il gère nativement le TTL (suppression automatique, sans job de purge), et c'est un service central que tous les serveurs web interrogent, ce qui rend ces serveurs sans état. Ses commandes atomiques (HINCRBY) et ses scripts Lua gèrent les accès concurrents (double clic, plusieurs onglets). MongoDB serait trop lent (disque, TTL purgé environ toutes les 60 s) ; des sessions en mémoire locale ne seraient pas partagées. Volume : 200 000 visiteurs actifs en pic représentent moins de 200 Mo de RAM. Déploiement : Sentinel (1 primaire, 2 réplicas, bascule automatique), en deux instances : sessions et paniers en noeviction (jamais évincés pour faire de la place), cache produit en allkeys-lru (évinçable sans risque).

CAP : plutôt AP. La réplication est asynchrone : lors d'une bascule, les dernières millisecondes d'écritures peuvent être perdues. Nuance : la bascule exige une majorité de sentinelles, donc un côté minoritaire perd l'écriture (pas de disponibilité totale) ; min-replicas-to-write limite les écritures perdues sur un primaire isolé. C'est acceptable, car perdre un « ajouter au panier » est une gêne mineure alors qu'un panier lent fait perdre des ventes. Surtout, la commande validée ne vit jamais dans Redis : au paiement, le stock est réservé dans MongoDB et la commande écrite dans Cassandra. Persistance : AOF everysec et RDB (au pire 1 s perdue).

Modèle de données : clés, structures, TTL

  • Hash plutôt que JSON pour le panier : HINCRBY modifie une ligne de façon atomique, donc deux ajouts simultanés donnent bien +2. Avec un JSON relu puis réécrit, on aurait une mise à jour perdue (lost update).
  • Le panier ne stocke pas les prix : le prix vient toujours du catalogue, ce qui évite d'afficher un prix périmé pendant les 7 jours de vie du panier.
  • TTL glissant : chaque action réarme le compteur (EXPIRE envoyé dans le même pipeline), ce qui traduit exactement « expiration après inactivité ».
  • Fusion à la connexion : le panier anonyme est fusionné dans le panier du compte par un script Lua, exécuté de façon atomique par Redis.

7. Lot 3 : Logs et analytics · Cassandra

Choix technologique

Cassandra écrit en append-only (commit log, memtable, SSTable), sans lecture préalable ni verrou : c'est l'un des moteurs les plus rapides en écriture. Son architecture sans maître (chaque nœud accepte les écritures) et sa scalabilité linéaire (on ajoute des nœuds à l'anneau) absorbent un volume qui croît pendant des années. Ses clustering columns trient les données sur disque, ce qui rend la lecture d'une période contiguë très efficace. MongoDB demanderait un sharding complexe à ce volume ; Redis est limité par la RAM. Contrepartie : pas de jointure, ni de GROUP BY libre, ni de tri sur une colonne quelconque. D'où une conception Query-Driven : une table par requête.

Hypothèses : environ 20 millions d'événements par jour, dont 10 % à l'heure de pointe, environ 250 octets par événement, partitions visées sous 100 Mo.

CAP : AP, à cohérence réglable par requête (facteur de réplication RF = 3). Logs : LOCAL_ONE en écriture et en lecture, pour le débit maximal. Commandes : LOCAL_QUORUM en écriture et en lecture, ce qui donne 2 + 2 > 3, soit R + W > RF : le client voit toujours sa dernière commande. Cette garantie suppose que la commande soit écrite avant d'être confirmée : l'API l'écrit donc de façon synchrone au paiement, sans passer par Kafka. Convention : day, hour et month sont calculés en UTC, comme event_time.

Des requêtes aux tables

Justification des clés

  • Journal brut (day, hour, bucket) : avec day seul, une partition pèserait 5 Go et concentrerait toutes les écritures du jour sur 3 nœuds (hot spot). Avec hour, on passe à 500 Mo à l'heure de pointe, ce qui reste trop. Avec un bucket = hash(session_id) % 8, on obtient environ 62 Mo, répartis sur le cluster. Le prix : lire une heure demande 8 requêtes parallèles, ce qui est acceptable pour une table d'archive.
  • event_id (timeuuid) en clustering : en Cassandra, un INSERT est un upsert. Sans cet identifiant, deux événements à la même milliseconde s'écraseraient.
  • (visitor_id, month) : ce time bucketing borne la partition d'un visiteur très actif (ou d'un robot), qui grossirait sinon sans limite.
  • Compteur product_views_by_day : la réponse est pré-agrégée (1 ligne lue au lieu de milliers d'événements). Environ 365 lignes par produit et par an, et la même table sert la tendance sur 7 jours (tranche contiguë).
  • Compteurs du jour (day, bucket) : avec day seul, chaque vue (ou recherche) de la journée frapperait la même partition, soit le hot spot évité pour le journal brut. bucket = hash(sku) % 8 (ou hash(term)) répartit les écritures ; le consommateur Kafka pré-agrège les incréments sur quelques secondes (views + 37 plutôt que 37 × + 1).
  • Top produits et recherches : Cassandra ne peut pas trier par la valeur d'un compteur. Un job horaire lit les 7 jours × 8 buckets de daily_views_by_product, additionne, trie, puis écrit le top 100 dans une table où le rang devient la clustering column (même principe pour les recherches). Pour un top en temps réel, un Sorted Set Redis (ZINCRBY) serait l'extension naturelle.
  • Commandes : les lignes sont imbriquées (list<frozen<order_item>>), avec le nom et le prix figés à l'achat, comme une facture. Écriture synchrone et idempotente (un INSERT rejoué réécrit la même ligne).

Écriture d'un clic et conservation

Un clic sur une fiche entraîne 4 écritures (journal brut, parcours du visiteur, 2 compteurs), envoyées en asynchrone et en parallèle par le consommateur Kafka. Nous n'utilisons pas de BATCH : un batch multi-partitions surcharge le coordinateur, et un batch ne peut pas mélanger compteurs et tables normales. La commande, elle, n'emprunte pas ce chemin : elle est écrite par l'API au paiement.

8. Lot 4 : Recommandations · Neo4j

Choix technologique

Les recommandations demandent de parcourir des relations sur plusieurs sauts. En relationnel, « ont aussi acheté » coûte 4 jointures sur des tables de millions de lignes, et le coût augmente à chaque saut. Neo4j stocke physiquement les relations (index-free adjacency) : suivre un lien coûte un saut de pointeur, indépendamment de la taille de la base. Cypher exprime les motifs de façon lisible. Neo4j ne remplace pas le catalogue : il ne stocke que l'identité des produits et leurs liens, alimentés par les change streams MongoDB et le flux des commandes.

CAP : les primaires valident les écritures par consensus Raft (majorité), donc CP. Les recommandations sont lues sur les read replicas, à cohérence éventuelle : une recommandation calculée sur des données vieilles de quelques secondes reste pertinente.

Modèle : nœuds, arêtes, propriétés

NœudPropriétés

Choix de modélisation

  • La compatibilité passe par des nœuds Standard. Des liens directs COMPATIBLE_WITH entre 50 CPU AM5 et 150 cartes mères AM5 demanderaient 7 500 relations. Avec un nœud AM5, il en faut 200, et une nouvelle carte mère devient automatiquement compatible avec tous les CPU AM5. USES et ACCEPTS sont distincts parce que la compatibilité n'est pas symétrique : un boîtier ATX accueille aussi l'ITX. Les contraintes numériques (longueur du GPU) restent des propriétés comparées dans la requête.
  • Nœud Order : il distingue « acheté dans la même commande » (signal fort, une configuration complète) de « acheté par le même client » (signal plus faible). Le prix : un saut de plus.
  • Supernœuds et BOUGHT_WITH : un produit phare présent dans 50 000 commandes rendrait le calcul en direct trop coûteux à chaque affichage. Les co-achats sont matérialisés dans BOUGHT_WITH {count} ; la fiche n'a plus qu'un saut à faire. Pour ne pas déplacer le problème dans un recalcul complet, la relation est incrémentée à l'ingestion de chaque commande (quelques paires par commande, ingestion idempotente), avec une réconciliation hebdomadaire. C'est la même logique que le pattern Computed du Lot 1.
  • Graphe minimal : pas de description, d'avis ni de données personnelles. Le graphe reste en mémoire et les parcours restent rapides.

Requêtes types (résultats attendus sur le jeu de démonstration)

// Q1. « Les clients qui ont acheté ce processeur ont aussi acheté cette carte mère »
MATCH (p:Product {sku: 'AMD-R7-7800X3D'})<-[:CONTAINS]-(o:Order)-[:CONTAINS]->(autre:Product)
      -[:IN_CATEGORY]->(:Category {name: 'Cartes mères'})
RETURN autre.name, count(DISTINCT o) AS commandes_communes ORDER BY commandes_communes DESC LIMIT 5
//  → ASUS TUF B650-Plus (2), MSI B650M Gaming Plus (1)

// Q1 bis. En production : relation matérialisée, un seul saut
MATCH (:Product {sku: 'AMD-R7-7800X3D'})-[r:BOUGHT_WITH]-(autre) RETURN autre.name, r.count ORDER BY r.count DESC LIMIT 5

// Q2. « Produits compatibles avec ce boîtier » : format accepté + longueur de GPU
MATCH (b:Product {sku: 'CM-NR200P'})-[:ACCEPTS]->(:Standard {kind: 'format'})<-[:USES]-(cm:Product)
RETURN 'Carte mère' AS type, cm.name AS produit
UNION
MATCH (b:Product {sku: 'CM-NR200P'}), (gpu:Product)-[:IN_CATEGORY]->(:Category {name: 'Cartes graphiques'})
WHERE gpu.lengthMm <= b.maxGpuLengthMm RETURN 'Carte graphique' AS type, gpu.name AS produit
//  → ASRock B650I (ITX), RTX 5070 (300 mm ≤ 336 mm) ; RTX 5090 (357 mm) exclue

// Q3. Configurateur : CPU → socket → carte mère → mémoire → RAM, et carte mère → format → boîtier (6 sauts)
MATCH (:Product {sku: 'AMD-R7-7800X3D'})-[:USES]->(:Standard {kind: 'socket'})<-[:USES]-(cm:Product)
      -[:IN_CATEGORY]->(:Category {name: 'Cartes mères'})
MATCH (cm)-[:USES]->(:Standard {kind: 'memoire'})<-[:USES]-(ram:Product)-[:IN_CATEGORY]->(:Category {name: 'Mémoire'})
MATCH (cm)-[:USES]->(f:Standard {kind: 'format'})<-[:ACCEPTS]-(boitier:Product)
RETURN cm.name, f.code, collect(DISTINCT ram.name), collect(DISTINCT boitier.name)

// Q5. Recommandations personnalisées (filtrage collaboratif, équivalent des « amis d'amis »)
MATCH (moi:Customer {id: 'U-42'})-[:PLACED]->(:Order)-[:CONTAINS]->(:Product)
      <-[:CONTAINS]-(:Order)<-[:PLACED]-(autre:Customer) WHERE autre <> moi
MATCH (autre)-[:PLACED]->(:Order)-[:CONTAINS]->(reco:Product)
WHERE NOT EXISTS { (moi)-[:PLACED]->(:Order)-[:CONTAINS]->(reco) }
RETURN reco.name, count(DISTINCT autre) AS clients_similaires ORDER BY clients_similaires DESC LIMIT 5
//  → ASUS TUF B650-Plus, Corsair DDR5 32 Go, RTX 5070 (2 clients chacun)

// Q7. Ingestion d'une commande (consommateur Kafka) : BOUGHT_WITH incrémental et idempotent
WITH {id: 'CMD-7', customer: 'U-42', date: date('2026-11-18'), items: ['AMD-R7-7800X3D', 'ASUS-B650-PLUS']} AS o
MERGE (c:Customer {id: o.customer}) WITH c, o WHERE NOT EXISTS { MATCH (:Order {id: o.id}) }
CREATE (c)-[:PLACED]->(ord:Order {id: o.id, date: o.date})
WITH ord, o UNWIND o.items AS sku MATCH (p:Product {sku: sku}) CREATE (ord)-[:CONTAINS {quantity: 1}]->(p)
WITH collect(p) AS ps UNWIND ps AS pa UNWIND ps AS pb WITH pa, pb WHERE pa.sku < pb.sku
MERGE (pa)-[r:BOUGHT_WITH]-(pb) ON CREATE SET r.count = 1 ON MATCH SET r.count = r.count + 1
//  → Ryzen 7 / ASUS B650-Plus passe de 2 à 3 ; rejouer l'événement ne change rien

Le fichier requetes.cypher contient aussi Q4 « produits similaires » (score : même gamme +3, même marque +2, +1 par standard technique commun, socket ou mémoire, le format physique étant exclu ; prix à ±30 %) et Q6 « produits pivots » pour composer des packs.

Conclusion

L'architecture proposée remplace la base monolithique par quatre bases spécialisées, chacune choisie pour la forme de ses données et de ses requêtes plutôt que par effet de mode. Le catalogue gagne la souplesse du modèle document, le panier la latence de la mémoire, l'analytique la puissance d'écriture d'un système distribué sans maître, et les recommandations l'expressivité du graphe.

Le fil conducteur est un arbitrage CAP explicite, donnée par donnée : la cohérence forte est réservée à ce qui engage financièrement LDLC (prix et stock, garantis par MongoDB ; commandes, lues et écrites en quorum dans Cassandra), et la disponibilité prime partout ailleurs. Les bases communiquent par événements (Kafka, change streams), ce qui permet à chacune d'évoluer et de passer à l'échelle indépendamment, notamment lors des pics de trafic liés aux sorties de composants.

Pistes d'évolution : top produits en temps réel avec un Sorted Set Redis, sharding MongoDB si le catalogue s'élargit (marketplace), algorithmes de similarité Neo4j GDS (Node Similarity) pour affiner les recommandations.
